# 设计台交互协议 · 1.5.1

让使用者随时知道当前在设计什么，以及本次要求改变了哪里。看板显示实际项目，不把示例或计划当成学员已经完成的成果。

## 六个视图

1. 设计工作台：当前任务与四阶段路线、实际文件统计、主结构图、具体设计决定、新需求和本次变化。
2. 设计结构：15 项职责。用“接收 → 动作 → 产出”讲明作用，课程例子明确标作例子；下面展示实际决定、正文、完整代码和逐段解释。
3. 结构图：执行流程展示实际节点、分支与出口，组成视图展示任务、模型、提示词、工具等全部结构决定。点击节点查看职责、读写字段、后续路由和源码位置。
4. 成果文件：真实文件列表、用途、调用关系、完整正文与函数位置；可保存文本草稿，生成文档须修改规范。
5. 运行记录：区分设计模拟、真实框架搭配模拟模型、真实模型；保留输入、输出、前后状态、错误、耗时与源码。
6. 项目交付：实际结构与成果校验、文档同步、代码待应用和导出。概念测验和学习笔记不参与设计过程。

## 每轮处理用户改动

开始时重读 teaching-state.json，尤其 design_requests 中 status=queued 的记录和网页已保存的决定。可用 design_engine.py --project "<项目>" --requests 列出需求。连续需求互相矛盾时只针对矛盾询问；已确定业务信息无需再确认。

逐条需求设置 current_module 与 learning_stage，修改 design 中的决定、图和契约；同步需要的正文/代码，再读回实际文件更新 artifacts 和解释。节点职责写具体输入、动作与输出，不能只有“处理节点”。仅改变提示词、模型或记忆配置时，组成卡更新是正确的可视化；没有执行路径变化则不虚构流程节点。

执行 design_engine.py --project "<项目>" --sync。同步器根据上一份实际规范生成 design_changes（最多 20 份），含前后图、决定、节点和连线差异；移动坐标不产生业务变化。不手工编造变化记录。

需求实际完成后执行 design_engine.py --project "<项目>" --resolve-request "<ID>" --basis "具体说明修改了哪些节点、配置和文件，以及尚待实现内容"。没有实际设计变化会拒绝完成标记。basis 必须真实对应该需求；无关设计变化不能当作满足需求。若请求本来已满足，向用户指出实际证据，不伪造变更来通过命令。

当前设计与已应用代码分开。修改图后若代码尚未更新，明确展示待应用项。代码模式更新实现并验证后再使用 --applied 记录依据。

## 自动同步与可视化

页面每 2.5 秒检测文件。没有网页草稿时自动刷新真实结果；有草稿时保留并提示冲突，先合并再保存。不能用聊天中记忆覆盖网页修改。新增绿色、更新金色、移除红色，历史前后图用于查看实际变化；配置差异在组成视图查看。

网页需求提交仅排队保存，不直接调用模型或唤醒宿主。下一轮 Skill 自动读取；使用者也可在 WorkBuddy 说“处理看板新需求”。离线 HTML 是可浏览、可导出的副本，不能写回本地项目。

## 共享当前步骤

编号、名称、顺序与阶段从 templates/step-registry.json 读取；15 个主步骤之外的安装、调试和预览均为本步骤操作。每轮教学先通过 --set-step 与 --action 写共享进度，再 --sync --progress，并用返回 label 作为聊天标题。网页切换调用 /api/progress，写同一个 current_module，下一轮 Skill 必须读回；切换不改变完成状态、设计图或运行证据。未保存草稿不会自动提交，版本冲突不会覆盖宿主的新进度。
